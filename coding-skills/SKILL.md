# 创建与修改代码

按任务范围完成以下四个阶段。

每次读取 `references/maintain-readme.md`，按其中规则建立、使用和维护项目 README。

## 1. 确认需求

确认目标、范围、约束和验收条件；关键缺口会改变结果或权限时向用户确认。

## 2. 计划方案

现有项目先通过 README 定位相关代码、配置和测试，核实当前行为、影响范围及工作区已有改动。从零项目确认运行环境；网络可用时，在设计和编码前检索 GitHub 同类项目，优先改造合适项目，否则借鉴设计或自行实现，记录选择依据。

需要设计项目结构、文件职责、公开接口或依赖关系时读取 `references/design-project.md`。

确定修改位置、执行顺序和验证方式。按需规划函数、模块、文件和目录的职责、公开接口、依赖方向及独立或内联的边界；结构取满足需求的最小规模，名称简洁直观并符合语言规范，行为用“动词 + 名词”，如 `resolve_data`。

## 3. 执行方案

按计划实施。破坏性操作、数据迁移、公共契约或关键依赖变更前先与用户确认。

**实现原则**：

- 优先评估标准库、已有实现和成熟依赖；复用外部代码或依赖时核实许可证、安全、维护与兼容性。
- 按计划封装内部实现，通过公开接口协作，并集中装配模块。
- 用满足需求的最少代码、抽象、配置和依赖；落实内联边界，共用规则与状态保留唯一实现。
- 在边界校验输入，明确错误、副作用和资源生命周期；按实际需要处理事务、并发、超时和重试。
- 结构变化时迁移调用方及配置、构建、测试引用，确认后清理旧实现；设计前提变化时修正计划。

**验收原则**：

- 根据改动选择测试、静态检查、构建或运行验证；缺陷修复核对复现与回归结果。
- 结构和接口变化后检查消费者与旧引用；失败后修正并复验。
- 记录实际检查、结果及未验证事项，并核对 README 与最终实现。

## 4. 交付结果

总结完成内容、关键决定、验证结果和剩余问题，只报告已核实的事实。
